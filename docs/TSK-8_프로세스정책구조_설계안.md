# TSK-8 프로세스 정책 구조 요구사항 정리

## 1. 목적

이 문서는 프로세스 커널 드라이버에서 사용할 정책 구조와 프로세스 실행 정보
구조를 정의한다. 현재 단계에서는 구현 방법을 확정하지 않고, 정책 리스트의
구조와 `DeviceIoControl` 동작을 요구사항 그대로 정리한다.

## 2. 리스트 관계

정책 전체를 연결하는 리스트와 정책별 실행 프로세스 리스트가 별도로 존재한다.

```text
정책 전체 리스트
PolicyListHead
  ├─ 프로세스 정책 구조체 1
  │    └─ ProcList
  │         ├─ 프로세스 정보 구조체 1 (PID 100)
  │         └─ 프로세스 정보 구조체 2 (PID 200)
  └─ 프로세스 정책 구조체 2
       └─ ProcList
            └─ 프로세스 정보 구조체 3 (PID 300)
```

- `PolicyListHead`는 설정된 모든 프로세스 정책을 연결한다.
- 각 정책 구조체의 `ProcList`는 해당 정책으로 실행이 허용된 프로세스 인스턴스를
  연결한다.
- 동일한 프로세스 이름으로 여러 프로세스가 실행되면 PID별로 프로세스 정보 구조체를
  각각 추가한다.

## 3. 프로세스 정책 구조체

프로세스 정책 구조체는 프로그램이 설정하는 실행 정책 하나를 나타낸다.

### 3.1 필드

| 필드 | 형식 | 필수 여부 | 의미 |
|---|---|---:|---|
| `PolicyListEntry` | `LIST_ENTRY` | 필수 | 정책 전체 리스트에서 다음 정책과 연결되는 리스트 헤더 |
| `ProcessName` | `UNICODE_STRING` | 필수 | 정책의 프로세스 이름 |
| `ProcessPath` | `UNICODE_STRING` | 선택 | 정책의 프로세스 전체 경로 |
| `IsSign` | `USHORT` | 선택 | 1 이상이면 코드 사인이 확인되어야 실행 허용 |
| `IsCmpFullPath` | `USHORT` | 선택 | 1 이상이면 프로세스 전체 경로를 비교 |
| `ProcList` | `LIST_ENTRY` | 선택 | 해당 정책으로 실행된 프로세스 정보 리스트의 헤더 |

정책의 기본 설정 정보는 `ProcessName`, `ProcessPath`, `IsSign`, `IsCmpFullPath`,
`ProcList`의 5개 필드로 구성된다. `PolicyListEntry`는 정책 구조체 자체를 정책
전체 리스트에 연결하기 위한 필수 헤더이다.

### 3.2 필드 동작

- `ProcessName`은 정책 검색에 사용하는 필수 프로세스 이름이다.
- `ProcessPath`는 전체 경로 비교가 필요한 정책에서 사용한다.
- `IsCmpFullPath`가 1 이상이면 프로세스 전체 경로가 있는 경우 정책의
  `ProcessPath`와 비교한다.
- 전체 경로가 정책과 일치하지 않으면 해당 프로세스는 실행할 수 없다.
- `IsCmpFullPath`가 1 이상인데 커널이 프로세스 전체 경로를 얻지 못한 경우에도
  실행을 허용하지 않는다.
- `IsSign`이 1 이상이면 코드 사인 확인 결과가 실행 허용이어야 한다.
- `IsSign`이 1 이상인데 사용자 모드 코드 사인 클라이언트가 없거나 응답 timeout이
  발생한 경우에도 실행을 허용하지 않는다.
- `ProcList`에는 해당 정책에 의해 실행이 허용된 프로세스 인스턴스를 연결한다.

## 4. 프로세스 정보 구조체

프로세스 정보 구조체는 실제 실행된 프로세스 하나를 나타낸다.

### 4.1 필드

| 필드 | 형식 | 필수 여부 | 의미 |
|---|---|---:|---|
| `ProcessListEntry` | `LIST_ENTRY` | 필수 | 소속 정책의 `ProcList`에 연결되는 리스트 헤더 |
| `ProcessId` | `Process ID` | 필수 | 실행 프로세스를 식별하는 값 |
| `ProcessHandle` | `HANDLE` | 필수 | 프로세스를 제어하기 위한 커널 핸들 |
| `ProcessPath` | `UNICODE_STRING` | 선택 | 실행된 프로세스의 전체 경로 |
| `Policy` | 프로세스 정책 구조체 포인터 | 필수 | 프로세스 이름에 해당하는 정책 구조체의 주소 |

### 4.2 필드 동작

- 같은 프로세스 이름이어도 `ProcessId`가 다르면 별도 프로세스 정보 구조체를 만든다.
- `ProcessPath`는 전체 경로 비교 옵션이 없더라도 실행된 프로세스 정보를 기록하기
  위해 저장할 수 있다.
- `Policy`는 이 실행 인스턴스가 어떤 프로세스 정책에 속하는지 나타낸다.
- `ProcessHandle`은 사용자 핸들이 아닌 커널 핸들로 저장하는 것을 우선한다. 커널
  핸들의 생성·보유 수명과 종료 시 정리가 안전한지 구현 단계에서 확인해야 하며,
  안전하게 보유할 수 없는 경우에는 참조된 `PEPROCESS`를 내부 기준으로 저장하고
  필요할 때 핸들을 연다.
- 프로세스가 종료되면 해당 프로세스 정보 구조체를 `ProcList`에서 제거한다.

## 5. 정책 설정 `DeviceIoControl`

정책 변경은 사용자 모드에서 `DeviceIoControl`을 통해 요청한다. 사용자 모드는
리스트 포인터를 전달하지 않고 정책 값과 프로세스 이름·경로를 전달하며, 커널이
정책 구조체와 리스트 노드를 생성한다.

### 5.1 설정(Set)

설정은 초기 정책 등록 또는 전체 정책 재구성이다.

1. 요청된 정책을 새 프로세스 정책 구조체로 구성한다.
2. 요청된 새 정책들을 새 정책 전체 리스트에 연결한다.
3. 기존에 실행 중인 프로세스 정보 구조체와 `ProcList` 노드는 삭제하지 않는다.
4. 실행 중인 각 프로세스 정보 구조체를 `ProcessName` 기준으로 새 정책에
   재연결하고, `Policy` 포인터를 새 정책 구조체로 갱신한다.
5. 모든 실행 중 프로세스의 재연결이 끝난 뒤, 더 이상 참조되지 않는 기존 정책
   구조체를 정책 전체 리스트에서 분리하고 해제한다.

설정 요청이 완료되면 정책 전체 리스트에는 요청으로 전달된 새 정책만 존재한다.
이미 실행 중인 프로세스 정보 구조체는 프로세스가 종료될 때까지 유지하며, 정책
교체만을 이유로 `ProcList`에서 제거하지 않는다.

### 5.2 추가(Add)

추가는 기존 정책을 유지하면서 새 정책을 추가한다.

1. 요청에는 하나 이상의 프로세스 정책이 포함될 수 있다.
2. 기존 정책과 중복되는 프로세스 정책이 있는지 확인한다.
3. 중복되면 기존 정책을 삭제한다.
4. 새로 요청된 정책을 기준으로 정책 전체 리스트에 추가한다.
5. 새 요청 안에서 같은 프로세스 정책이 여러 번 나오면 마지막으로 추가된 정책을
   기준으로 한다.

중복 정책의 판단 기준은 요청한 프로세스 이름을 기준으로 한다. 따라서 중복된
과거 정책은 삭제되고 새로 추가된 정책이 남는다.

### 5.3 제거(Remove)

제거는 프로세스 이름 목록을 받아 일치하는 정책을 삭제한다.

1. 요청에는 하나 이상의 삭제 대상 프로세스 이름이 포함될 수 있다.
2. 정책 전체 리스트에서 요청된 프로세스 이름과 일치하는 정책을 찾는다.
3. 일치하는 정책의 `ProcList`에 연결된 프로세스 정보 구조체를 먼저 제거한다.
4. 정책 구조체를 정책 전체 리스트에서 제거한다.
5. 요청 이름과 일치하지 않는 정책은 유지한다.

## 6. 프로세스 실행 처리

프로세스가 실행되면 커널은 정책 전체 리스트에서 프로세스 정책을 검색한다.

```text
프로세스 실행
  → PolicyListHead에서 ProcessName 검색
  → 일치하는 프로세스 정책 확인
  → IsCmpFullPath 확인
  → IsSign 확인
  → 조건 일치: 프로세스 정보 구조체 생성
  → 해당 정책의 ProcList 마지막에 연결
```

### 6.1 프로세스 이름 검색

- 실행된 프로세스의 이름으로 정책 전체 리스트를 검색한다.
- 프로세스 이름에 해당하는 정책 구조체를 찾으면 해당 정책의 조건을 확인한다.

### 6.2 전체 경로 비교

- `IsCmpFullPath`가 1 이상이면 프로세스 전체 경로를 정책의 `ProcessPath`와 비교한다.
- 전체 경로가 정책과 일치하지 않으면 실행을 허용하지 않는다.
- `IsCmpFullPath`가 1 이상인데 커널이 전체 경로를 얻지 못하면 실행을 허용하지
  않는다.
- 전체 경로 비교를 사용하지 않는 정책은 프로세스 이름 기준으로 처리한다.

### 6.3 코드 사인 확인

- `IsSign`이 1 이상이면 사용자 모드의 코드 사인 확인이 필요하다.
- 커널은 프로세스 전체 경로를 사용자 모드 애플리케이션에 전달한다.
- 사용자 모드 애플리케이션은 전달받은 전체 경로의 코드 사인 여부를 확인한다.
- 사용자 모드 애플리케이션은 확인 결과를 커널에 반환한다.
- 커널은 반환된 결과에 따라 실행 허용 여부를 결정한다.
- 사용자 모드 클라이언트가 없거나 정해진 시간 안에 응답하지 않으면 실행을
  허용하지 않는다.
- 이 통신은 `DeviceIoControl`을 통한 동기 방식으로 동작한다.

### 6.4 실행 허용 시 처리

전체 경로 비교와 코드 사인 확인을 포함한 정책 조건이 실행 허용이면 다음 정보를
담은 프로세스 정보 구조체를 만든다.

- `ProcessId`
- `ProcessHandle`
- 실행된 프로세스의 `ProcessPath`
- 일치한 프로세스 정책 구조체 포인터 `Policy`

새 프로세스 정보 구조체는 해당 정책 구조체의 `ProcList` 마지막에 연결한다.

### 6.5 프로세스 종료 시 처리

프로세스 종료 통지가 오면 `ProcessId`가 일치하는 프로세스 정보 구조체를 찾아
해당 정책의 `ProcList`에서 제거한다. 제거 후 프로세스 핸들과 경로 등 해당 노드의
자원을 정리한다.

## 7. 구현 시 리스트 수명 규칙

- 정책 전체 리스트의 헤더는 드라이버가 소유한다.
- `Remove` 또는 드라이버 언로드로 정책 구조체를 삭제할 때는 해당 정책의
  `ProcList`를 비운다. `Set`으로 전체 정책을 교체할 때는 기존 실행 노드를
  삭제하지 않고 새 정책에 재연결한 뒤, 참조가 없는 기존 정책만 해제한다.
- 프로세스 정보 구조체를 삭제할 때는 먼저 리스트에서 연결을 해제한다.
- 정책 검색·추가·제거와 프로세스 생성·종료 콜백이 동시에 실행될 수 있으므로 리스트
  접근은 커널 잠금으로 보호한다.
- 사용자 모드 요청에는 커널 리스트 주소나 `UNICODE_STRING.Buffer` 포인터를 넣지 않는다.
- 드라이버 언로드 시 정책 리스트와 모든 `ProcList`를 순서대로 정리한다.

## 8. 확정된 예외 및 갱신 규칙

- 전체 경로 비교가 켜져 있는데 커널이 전체 경로를 얻지 못하면 차단한다.
- 코드 사인 확인이 필요한데 사용자 모드 클라이언트가 없거나 timeout이면 차단한다.
- 중복 정책의 식별 기준은 `ProcessName`만 사용한다. 전체 경로는 중복 식별 키에
  포함하지 않는다.
- 전체 정책 교체 때 이미 실행 중인 프로세스의 `ProcList` 노드는 제거하지 않는다.
  새 정책 목록의 동일한 `ProcessName` 정책에 노드를 다시 연결하고 `Policy`
  포인터를 갱신한다.
- `ProcessHandle`은 안전성이 확인되는 경우 커널 핸들 값을 보유한다. 커널 핸들
  수명 관리가 안전하지 않다고 판단되면 참조된 `PEPROCESS` 보관 방식으로
  전환한다.

새 정책 목록에 동일한 `ProcessName`이 없는 실행 중 프로세스는 정책 교체만으로
종료하거나 `ProcList`에서 삭제하지 않는다. 이 경우의 보관 위치와 이후 정책
재연결 방식은 구현 단계에서 별도 관리 규칙(예: 보류 목록)을 정해야 한다.
