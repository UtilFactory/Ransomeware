# 부팅 영역 보호 시험 프로그램

## 1. 목적과 현재 범위

`UF_BootProtectionTest.exe`는 C로 작성한 사용자 모드 콘솔 시험 도구다.
부팅 영역 보호 설계의 구간 판정과 유지보수 허용 검증을 먼저 시험한다.
기본 `--self-test`·`--image-test`는 관리자 권한·드라이버 설치·VM 연결이 필요하지 않다.
`--vhdx-damage`와 `--vhdx-protection-test`는 Hyper-V 게스트의 관리자 권한과 VM 검사점을 요구한다.

**랜섬웨어가 아니다.** 기본 합성 모드는 물리 디스크·볼륨을 열지
않으며, 기존 파일·장치 경로를 명령줄로 입력받지 않는다. VHDX 모드도
프로그램이 새로 만든 폐기용 VHDX만 대상으로 하며, 기존 디스크·경로는 거부한다.
프로세스 종료·파일 격리·삭제 기능은 없다.

`FAT32`, `NTFS`, `MBR`, `GPT` 이름을 붙인 영역은 합성 시험 데이터다. `.fixture.bin`
파일에 유효한 파일시스템이나 부팅 코드를 만들지 않으며 실제 배치·BPB를 파싱하지 않는다.
이 시험이 통과해도 현재 파일·프로세스 드라이버가 실제 부팅 영역을 보호한다는 의미는 아니다.

## 2. 실행

저장소 루트에서 PowerShell로 실행한다.

```powershell
# 파일 생성 없이 합성 구간·허용 정책 검사
.\x64\Debug\bin\UF_BootProtectionTest.exe --self-test

# 새 일반 파일에서 모의 쓰기와 내용·SHA-256 확인
.\x64\Debug\bin\UF_BootProtectionTest.exe --image-test

# 위 두 시험을 모두 실행
.\x64\Debug\bin\UF_BootProtectionTest.exe --all
```

`--help` 또는 인수 없는 실행은 사용법을 출력한다.
지원하지 않는 인수나 추가 경로를 주면 시험을 시작하지 않고 종료 코드 2를 반환한다.

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 요청한 시험 통과 또는 도움말 표시 |
| 1 | 검사 실패 또는 파일·해시 등 시험 인프라 오류 |
| 2 | 잘못된 명령줄 |

## 3. 검사 항목

- 512·4096바이트 논리 섹터를 각각 사용하는 합성 배치
- 보호 영역 내부, 시작/끝 경계 일치, 한 바이트 경계 교차, 여러 영역을 덮는 큰 요청
- 디스크 끝, 0 길이, 범위 초과, 64비트 오버플로
- 잘못된 정책의 개수·영역 ID·중복·겹침·정렬·섹터 정렬 검증
- 요청자 미확인, PID·생성 식별자·장치·정책 세대 불일치
- 유지보수 허용의 유효 기간, 허용 영역·범위 제한, 잘못된 허용 데이터
- 독립적인 바이트 보호 비트맵과 비교하는 재현 가능한 무작위 요청 10,000개씩

30개 명명된 시나리오를 각 섹터 크기에서 실행한다. `--self-test`의 85개 검사에는
두 무작위 묶음 검사도 포함하며, 개별 무작위 요청 총수는 20,000개다.
`--image-test`는 같은 30개 시나리오를 두 일반 파일에서 실행하여 60개를 검사한다.
전체 `--all`의 판정·내용 검사는 145개다. 무작위 요청 수를 별도 시험 함수 개수와 혼용하지 않는다.

모델의 결과는 다음과 같다.

| 값 | 의미와 시험 파일 처리 |
| --- | --- |
| `ALLOW` | 보호 범위 밖 또는 유효한 유지보수 허용. 새 시험 파일의 요청 범위만 변경 |
| `BLOCK` | 보호 영역 무허가 쓰기. 파일 쓰기를 호출하지 않음 |
| `INVALID` | 정책·요청 입력 또는 세대 오류. 파일 쓰기를 호출하지 않음 |
| `NOT_COVERED` | 다른 장치 토큰. 보호 성공이라 하지 않으며 시험 파일도 변경하지 않음 |

`BLOCK`은 현재 사용자 모드 모델의 판정이다. 커널에 쓰기를 보낸 뒤 거부 응답을
받는 시험이 아니다. 따라서 보호 드라이버의 실패 코드나 이벤트 수신을 검증하지 않는다.

## 4. 폐기용 VHDX 실제 손상 시험

Hyper-V Win11 게스트에서 관리자 PowerShell로 다음 명령을 실행하면 프로그램이 로컬
임시 폴더에 **새 256MiB VHDX만** 만들고, FAT32 또는 NTFS로 포맷한 뒤 기본·백업
부트 섹터의 부팅 코드와 `0x55AA` 서명을 0으로 변경한다.

```powershell
.\x64\Debug\bin\UF_BootProtectionTest.exe --vhdx-damage FAT32 --confirm-disposable-vhdx
.\x64\Debug\bin\UF_BootProtectionTest.exe --vhdx-damage NTFS  --confirm-disposable-vhdx
```

실행 전 VM 검사점을 만들고 해당 VM에 복구 가능한 추가 디스크가 없는지 확인한다.
이 모드는 기존 경로·`PhysicalDriveN` 인수를 받지 않으며, Hyper-V 게스트 식별·승격된
토큰·`File Backed Virtual` 버스·256MiB RAW 디스크·512바이트 섹터를 모두 확인한다.
검증에 실패하면 포맷이나 쓰기를 시작하지 않는다. 생성된 VHDX와 `boot-before.bin`,
`boot-after.bin`, `run.log`, `result.json`은 자동 삭제하지 않는다.

`--vhdx-damage`에서는 `kernelProtectionVerified=false`가 정상이다. 이 모드의 성공은
“폐기용 VHDX의 손상 쓰기가 실제로 재현됨”만 의미하며, 보호 드라이버 통과를 의미하지 않는다.
2026-09-14에 추가한 실제 커널 비교 모드는 아래 4.1절과 같이 별도로 실행한다.
실제 랜섬웨어 샘플은 사용하지 않는다.

### 4.1 UI 시작·정지와 커널 차단 비교

```powershell
.\UF_BootProtectionTest.exe --vhdx-protection-test FAT32 --confirm-disposable-vhdx
.\UF_BootProtectionTest.exe --vhdx-protection-test NTFS --confirm-disposable-vhdx
```

위 명령은 공용 `bin`을 현재 폴더로 한 경우다. 사전에 시험 서명과 새 패키지를 준비하고
[부트 보호 사용법](부팅영역보호_사용법.md)의 UI 절차를 따른다.

1. 프로그램이 새 VHDX를 만들고 포맷한 뒤 대기한다. UI에서 해당 디스크에 필터를 등록한다.
2. 안내에 따라 Enter를 누르면 프로그램이 VHDX를 분리·재부착한다. UI에서 새로고침한다.
3. 필터가 실제 부착된 동일 디스크의 정지 상태를 확인한다. UI에서 `부트 영역 방어 시작`을 누른다.
4. 방어 중 상태를 확인하고 진행하면 기본·백업 부트 섹터 쓰기가 각각 Win32 오류 5로
   거부되는지, 내용이 동일한지, 같은 장치 ID·정책 세대의 차단 횟수가 2 증가하는지 확인한다.
5. UI에서 `부트 영역 방어 정지`를 누른 뒤 진행한다. 같은 쓰기가 성공하고 새 VHDX의
   두 섹터가 실제 변경되어야 한다. 차단과 해제 후 쓰기까지 모두 확인해야
   `kernelProtectionVerified=true`를 기록한다.

`boot-before.bin`, `boot-protected-after.bin`, `boot-stopped-after.bin`, `run.log`,
`format.log`, `result.json` 및 VHDX를 보존한다. UI 차단 로그의 PID·경로·오프셋도 함께
확인한다. 전역 이벤트 큐를 UI가 소비하므로 CLI는 이벤트를 빼앗지 않고 장치별 카운터를 검사한다.
어느 단계에서든 식별·검증에 실패하면 실패로 종료하며 차단 성공이라고 기록하지 않는다.
이 모드는 MBR/GPT·장치 제어 명령·동시 PnP·Verifier 검증을 대신하지 않는다.

## 5. 파일 모의 시험과 보고서

실행마다 로컬 고정 드라이브의 임시 경로 아래에 무작위 이름의 새 폴더를 만든다.
폴더와 파일의 재분석 지점 여부를 검사하고, 파일은 `CREATE_NEW`와 공유 금지로 연다.
검사한 핸들을 계속 사용하며 기존 파일을 열거나 덮어쓰는 옵션을 제공하지 않는다.

```text
%TEMP%\UF_BootProtectionTest_<무작위 식별자>\
  synthetic-512.fixture.bin     1 MiB
  synthetic-4096.fixture.bin    8 MiB
  result.json
```

프로그램이 실제 생성한 폴더와 보고서의 전체 경로를 출력한다. 시험 자료는 자동으로
삭제하지 않으므로 필요 없을 때 표시된 해당 시험 폴더만 사용자가 정리할 수 있다.

각 요청 전후에 파일 전체를 읽어 SHA-256을 계산한다. `BLOCK`, `INVALID`,
`NOT_COVERED`는 해시와 내용이 모두 유지되어야 한다. `ALLOW`는 지정한 바이트만
바뀌고 나머지 바이트는 유지되어야 한다. 허용 요청도 시험 파일 경계를 다시 검사한다.

보고서는 UTF-8 JSON이며 다음을 포함한다.

- `mode=regular-file-simulation`, `kernelDriverTested=false`, `realDiskWritten=false`
- 시나리오명, 섹터 크기, 요청 위치·길이, 기대/실제 판정, 이유 코드, 영역 ID
- 실제 파일 쓰기 호출 여부, 전후 SHA-256, 각 시나리오 성공 여부
- 시험 완료 여부, 파일 시나리오 수, 해당 실행의 검사 수와 실패 수

JSON을 완성하기 전의 파일 I/O·해시 오류는 `completed=false`로 표시한다.
보고서 생성·기록 자체가 실패하면 보고서가 없거나 불완전할 수 있으므로 종료 코드와
콘솔의 `stage`, `GetLastError`, `NTSTATUS`를 함께 확인한다. 두 오류 코드 계열은 구분한다.

## 6. 소스와 빌드

- `UF_BootProtectionTest/include/uf_boot_range.h`: 내부 모델 형식
- `UF_BootProtectionTest/src/uf_boot_range.c`: 파일 I/O 없는 구간·허용 판정
- `UF_BootProtectionTest/src/main.c`: 독립 기준 검사, 안전한 파일 모의 시험, 보고서

모델은 최대 64개 비중첩·위치순 영역을 검사한다. 허용 하나는 정확한 장치·정책 세대·
PID·생성 식별자·영역·바이트 범위·만료 시각에 묶는다. 이는 통신 ABI가 아니며
사용자 입력의 `RequestorKnown`을 실제 드라이버에서 신뢰해도 된다는 의미가 아니다.

솔루션에 Debug/Release x64 프로젝트를 추가하고 두 공용 `bin` 경로로 EXE를 복사한다.
정적 C 런타임을 사용하고 별도 통신 DLL에 의존하지 않는다.

## 7. 검증 결과 (2026-09-11)

- 전체 솔루션 `Debug | x64`, `Release | x64` Rebuild 성공: 각각 경고 0개, 오류 0개.
- 두 구성의 `--all`: 각각 145개 검사, 실패 0개. 파일 시나리오 60개와 독립 비트맵 비교 20,000개 요청 포함.
- Release JSON: `completed=true`, `caseCount=60`, `checks=145`, `failedChecks=0` 확인.
- 일반 파일 시나리오 판정: `ALLOW` 8개, `BLOCK` 42개, `INVALID` 8개, `NOT_COVERED` 2개.
- 추가 장치 경로 인수는 종료 코드 2로 거부하며, UNC 임시 경로는 파일 생성 전에 종료 코드 1과 `GetLastError=161`로 거부.
- 개발 호스트에서 사용자 모드 시험만 실행했다. VM 드라이버 설치·실제 부팅 영역 쓰기·UI 알림·프로세스 종료·격리는 시험하지 않았다.
- 개발 호스트의 `--vhdx-self-test`는 14개 파서 검사를 통과했고, `--vhdx-damage`는
  Hyper-V 게스트가 아니므로 `GetLastError=50`으로 안전하게 거부됐다. 실제 손상 모드는
  검사점이 설정된 Win11 VM에서만 실행한다.

## 8. 참고 위협 사례

부트 영역을 바꾸는 악성코드는 파일 암호화 랜섬웨어와 파괴형 와이퍼가 섞여 있다.
공식 분석에서 확인되는 사례는 다음과 같다.

- `Petya`/`NotPetya`: Microsoft는 MBR을 덮어쓰고 시스템 드라이브 섹터를 암호화한다고 설명한다.
  [Microsoft Security Intelligence - Win32/Petya](https://www.microsoft.com/en-us/wdsi/threats/malware-encyclopedia-description?Name=Win32%2FPetya)
- `WhisperGate`: Microsoft는 랜섬웨어처럼 보이는 파괴형 악성코드가 MBR을 덮어쓴 사례로 분석한다.
  [Microsoft Security Blog - destructive malware](https://www.microsoft.com/en-us/security/blog/2022/01/15/destructive-malware-targeting-ukrainian-organizations/)
- `WipMBR` 계열: Microsoft가 MBR과 비시스템 디스크 파티션 데이터를 덮어쓰는 트로이목마로 분류한다.
  [Microsoft Security Intelligence - WipMBR](https://www.microsoft.com/en-us/wdsi/threats/malware-encyclopedia-description?Name=Trojan%3AWin64%2FWipMBR.gen%21A)

이 사례들은 특정 `FAT32` 또는 `NTFS` 파일만 노린다는 뜻이 아니라, 디스크·볼륨의
부트 섹터/MBR 같은 원시 영역을 대상으로 한 사례다. 따라서 시험은 두 파일시스템의
정상 부트 레이아웃을 각각 만든 뒤 같은 무허가 섹터 쓰기를 차단하는지 확인해야 한다.
실제 샘플을 VirusTotal에서 내려받아 실행하지 않고, 이 도구의 합성·폐기용 VHDX
시나리오를 사용한다.

## 9. 후속 통합 시험

다음 단계는 신규 스토리지 필터의 관찰·차단 경로 구현과 이 도구의 전용 VHDX 쓰기 차단 통합 시험이다.
실제 장치 시험은 장치 신원·부착 상태·허용된 폐기용 디스크·복구 수단을 검증하는
별도 명령으로 설계해야 한다. 이 프로그램에 임의 디스크 쓰기 옵션을 먼저 추가하지 않는다.
UI 알림·종료·격리는 해당 모듈 구현 후 별도의 시험 프로세스와 검증한다.
