# 부팅 영역 보호 이관 누락 수정

작성일: 2026-09-15 · 브랜치: `tsk/8/main`

## 1. 보고와 확인 범위

사용자는 부트 보호가 정상적으로 시작된 뒤 악성코드 시험을 했으나 방어되지 않았고,
VM이 부팅되지 않아 새 로그를 확보할 수 없다고 보고했다. 앞선 로그에서 확인했던
구형 DriverStore 패키지 및 프로세스 DLL 로드 오류를 이번 미차단의 확정 원인으로
사용하지 않는다. 손상 위치·요청 모드·실제 I/O 경로는 확보되지 않았다.

참고 구현과 현재 소스를 대조하여 동작 차이는 확인했다. 이 수정은 그 차이와 검사
실패 통과를 보완한 것이며, 해당 악성코드의 원인 규명이나 VM 실방어 성공을 의미하지 않는다.
참고 구현을 제공받아 통합·보완한 경위와 이번 수정은 구분한다.

## 2. 수정 내용

1. `driver.c`에서 원시 쓰기 부트 분기를 일반 파일 정책의 KernelMode 제외보다 먼저
   처리한다. 일반 파일 정책은 이전처럼 커널 기원 I/O를 제외한다.
2. `boot_guard.c`의 KernelMode 전체 및 PID 0/4 일괄 예외를 제거한다. 비페이징 커널
   쓰기도 검사한다. 원본의 KernelMode이면서 페이징 I/O인 예외와 참조된 현재 관리
   클라이언트 예외는 유지한다. KernelMode와 정상 시스템 유지보수 허용은 같은 의미가 아니다.
3. 활성 상태에서 원시 볼륨/장치로 분류된 선두 2KiB 쓰기는 대상 재검증·MDL 잠금·
   메모리 할당·작업 큐·재열기·읽기·비교 실패 때 통과시키지 않고 `STATUS_ACCESS_DENIED`,
   완료 바이트 0으로 끝낸다. 이미 정지했거나 관리 클라이언트로 바뀐 요청에는 새 차단을
   적용하지 않는다. 오류 알림 전송 실패는 차단 결정을 취소하지 않는다.
4. 1MiB 전체 쓰기 스냅숏과 동시 16개 제한은 메모리 안전을 위해 유지하되 초과 요청은
   검사 실패 차단으로 처리한다. 한도를 없애거나 읽기 실패를 안전하다고 간주하지 않는다.
5. 동일 선두 바이트를 허용할 때는 승인한 스냅숏만 하위 계층으로 전달한다. 버퍼 변경
   경쟁을 다시 만들거나 잠금 없는 사용자 포인터를 worker에서 읽는 원복은 하지 않는다.
6. `[UF][boot] revision=20260915.1`에 단계·원래 NTSTATUS·PID/TID·모드·IRQL·IRP flags·
   위치·길이를 기록한다. 실패 원인은 커널 진단에 남기고 UI에는 차단 결과를 구분한다.

## 5. 배포와 남은 제한

- 생성물 위치는 `x64/Debug/bin`, `x64/Release/bin`이다. 같은 구성의 SYS/INF/CAT,
  DLL·UI를 함께 배포해야 한다. 이번 작업에서는 호스트/VM 드라이버 설치·로드를 하지 않았다.
- 사용자의 부팅 불가 VM·검사점·가상 디스크와 로그 파일을 변경하지 않았다. 복구는 별도
  작업이며 악성코드 재실행은 하지 않았다. 깨끗한 격리 VM 검사점에서 비악성 검증을 먼저
  수행해야 한다. 기존 손상 도구 실행 성공을 방어 시험 성공으로 사용하지 않는다.
- 콜백에 도달하지 않는 직접 디스크 I/O, 원시 대상 분류 자체에 실패하는 요청, 선두
  2KiB 밖의 전체 GPT 엔트리·백업 GPT·EFI 영역은 이번 수정으로 보호 완료가 되지 않는다.
  관리 클라이언트·커널 페이징 예외도 남는다. [2차 계획](부팅영역보호_2차계획.md)은 미착수다.
- 확인한 보호 구간의 정상 쓰기도 비교 불가/상한 초과면 거부할 수 있다. 일반 OS 작업,
  디스크 관리·업데이트·복구·잠긴 볼륨·시작/정지·언로드 호환성을 VM에서 검증해야 한다.
- 실제 차단 확인은 설정 성공뿐 아니라 콜백 도달, API 거부 결과, 차단/실패 수,
  시험 전후 보호 구간 내용 보존을 함께 확인해야 한다. 실방어 완료로 배포하지 않는다.

## 8. 후속 표시 수정: 차단 결과와 검사 오류 구분 (`6231ba0`)

### 변경 배경

사용자가 제공한 후속 화면에는 `2026-09-15 01:09:47.140`, PID `14316`, 대상 장치
`\Device\Harddisk0\DR0`에 대한 `부트 검사 실패(차단)` 사건이 표시되어 있었다.
이 문구는 쓰기를 막았는데도 보호 자체가 실패했다는 의미로 읽힐 수 있어,
`부트 쓰기 차단 — 검사 오류`로 변경했다. 앞부분은 요청의 처리 결과이고 뒷부분은 이유다.

### 로그의 정확한 의미

| Action | UI·텍스트 로그·CLI 표시 | 처리 결과와 해석 |
| --- | --- | --- |
| 5 | 부트 영역 차단 | 보호 구간의 기존 내용과 쓰려는 내용이 달라 해당 쓰기를 거부했다. 디스크가 이미 변경됐다는 뜻이나 악성코드 종류의 판정은 아니다. |
| 6 | 부트 검사 실패(통과) | 구버전에서 검사를 완료하지 못하고 요청을 통과시킨 사건이다. 기존 로그와의 호환성을 위해 차단으로 재해석하지 않는다. |
| 7 | 부트 쓰기 차단 — 검사 오류 | 검사 준비·재열기·읽기 등에서 오류가 발생하여 안전 여부를 확인하지 못했고, 보수적으로 해당 쓰기를 거부했다. 검사 실패가 차단 실패를 뜻하지 않는다. |

Action 7의 커널 처리 결과는 `STATUS_ACCESS_DENIED`, 완료 바이트 `0`이다.
내용 비교를 완료하지 못했으므로 실제 악성 데이터였다고 단정할 수 없다. 정상적인 디스크
관리·복구 요청도 검사 오류나 자원 상한 때문에 이 결과를 받을 수 있다.
이 사건 하나가 UI나 드라이버 전체의 작동 중단을 뜻하는 것도 아니다.
차단 수(`BlockedWrites`)와 검사 실패 수(`InspectionFailures`)에 모두 포함되는 사건이므로,
두 수를 더해 전체 요청 수로 해석하면 안 된다.

### 이번 화면으로 확인되는 것과 추가 진단

- 제공된 화면은 Action 7 사건이 UI에 도달해 표시되었다는 근거다. 사용자의 차단 확인
  보고와는 별도로, 에이전트가 VM의 실제 쓰기 결과·보호 영역 보존·재부팅 성공을 직접
  검증한 것은 아니다. 이 한 줄로 모든 부팅 영역의 방어 성공을 선언하지 않는다.
- 해당 요청에서 어떤 검사 단계가 실패했는지는 화면만으로 알 수 없다. 재열기·읽기·
  메모리/큐 준비·한도 초과 등은 가능한 분기이며, 이번 사건의 확정 원인이 아니다.
- 같은 시각과 PID의 커널 진단 `[UF][boot] revision=20260915.1`에서 `stage`, 원래
  `NTSTATUS`, 요청 모드·위치·길이를 확인해야 정확한 원인을 좁힐 수 있다. 이 커널
  진단은 별도 디버그 출력이며 UI 로그 파일에 자동 수집되는 것으로 가정하지 않는다.
  원래 NTSTATUS는 현재 공유 이벤트에 포함되어 있지 않다.
- UI의 `설정 활성`은 기능의 활성 플래그다. 검사 성공이나 전체 저장장치 경로 보호를
  뜻하지 않는다. 보호 범위와 남은 예외는 위 5절 및 [2차 계획](부팅영역보호_2차계획.md)을 따른다.

### 변경 범위와 배포

- UI의 사건 이름 변환과 이를 사용하는 텍스트 로그, `UF_FileFilterTest`의 CLI 문구를
  일치시켰다. 구분 열은 내용에 맞춰 늘어나며 전체 문구 툴팁을 제공한다.
  PID·요청 프로세스 이미지 경로·대상 경로 열의 최소폭은 유지한다.
- 이 후속 수정은 Action 번호·공유 ABI·차단 정책·커널 코드 변경이 아니다.
  **이미 `a89b08d`의 검사 실패 차단 드라이버를 설치한 환경**에서는 같은 구성의
  `RansomUtilFactory.UI.exe`와 `RansomUtilFactory.UI.dll`을 교체하고 UI를 재실행하면 된다.
  CLI도 사용하는 경우 `UF_FileFilterTest.exe`를 함께 교체한다. 표시 변경만을 위한
  SYS 재설치는 필요 없다.
