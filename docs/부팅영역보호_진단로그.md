# 부팅 영역 보호 시작·조회 실패 진단 로그

작성일: 2026-09-14 · 브랜치: `tsk/8/main`

## 1. 관찰된 증상과 이번 변경

사용자 VM 화면에서 보호 시작과 상태 조회가 모두 `GetLastError=1 (0x00000001)`로 실패했다.
보호 상태는 미확인이다. 이 화면만으로 보호가 시작되었거나 정지되었다고 판단하지 않는다.

현재 SET(명령 5)과 QUERY(명령 6)는 메모리의 활성 상태·카운터를 처리한다. 이 단계는
실제 부트 영역 쓰기·비교 읽기와 다르므로 저장장치 검사 실패로 단정하지 않는다.
구버전/다른 드라이버의 명령 미지원 등을 확인할 수 있도록 UI·DLL·커널 단계 로그를 추가했다.
오류 원인을 확정하거나 보호 정책·설치 방식·통신 ABI를 변경한 수정은 아니다.
2차 디스크 드라이버 전환도 이번 작업에 포함하지 않는다.

## 2. 사용자에게 필요한 수집 절차

1. 시험 VM의 기존 UI를 종료하고 최신 `x64\Debug\bin`의 UI와 DLL을 같은 실행 폴더에
   복사한다. 처음에는 현재 실패 상태에서 사용자 모드 로그를 수집해도 된다.
2. 관리자 권한으로 UI를 실행하고 파일 필터에 연결한다. `시작`은 한 번만 누르고,
   요청 결과가 표시될 때까지 기다린다. 필요하면 그 뒤 `상태 새로 고침`을 한 번 누른다.
3. 해당 실행 폴더의 `logs`에 있는 다음 파일과 결과 화면을 함께 전달한다.
   - `RansomUtilFactory.UI.log`
   - `uf_fltwarp.log`
   - `uf_fltwarp.bootstrap.log`
4. 눌렀던 시각, VM 재부팅 여부, 이번에 SYS까지 재설치했는지도 함께 기록한다.
   오류를 재현하기 위해 실제 부트 영역을 쓰거나 악성코드를 실행할 필요는 없다.

UI·DLL 로그는 자동으로 파일에 기록한다. 이전 로그를 지우지 않아도 요청 식별자와 시각으로
구분할 수 있다. 경로·PID가 포함되므로 전달 전에 불필요한 개인 경로 노출 여부를 확인한다.

## 3. 로그별 확인 항목

| 로그 | 식별자와 핵심 내용 |
| --- | --- |
| UI | `[FileBoot requestId=... command=Start/Stop/Query]`, 연결 세대·진입/건너뜀·게이트·SET/QUERY 반환·예외·지연 결과 억제·완료 시간 |
| UI 배포 정보 | `file-boot-ui-20260914.1`, UI 경로·MVID, 실제 로드 DLL 경로, 배포/서비스 SYS 파일의 크기·수정 시각·SHA-256 |
| UI 설치/로드 | 선택 INF 경로, `DiInstallDriverW` 결과·재부팅 필요 여부, `FilterLoad/FilterUnload` 원시 HRESULT와 이미 로드됨 |
| DLL | `FileBootDiag=20260914-1`, 빌드 시각·Debug/Release·실제 DLL 경로, 요청별 `requestId`, command/version/크기, callerTid/workerTid, 원시 HRESULT·최종 오류·수신 크기·검증 단계 |
| 부트스트랩 | 로거 초기화 및 `FilterSendMessage` 시작·종료·시간 초과의 보조 기록 |
| 커널 디버그 출력 | `[UF][control]`, `file-boot-trace-20260914.1/Debug` 또는 `/Release`, 수신 헤더·검증 거부 분기·활성 변경·응답 크기·최종 NTSTATUS·소요시간 |

UI·DLL·커널의 요청 번호는 각각의 로컬 식별자이며 같은 값이라는 뜻이 아니다.
UI의 네이티브 스레드 ID와 DLL callerTid, DLL workerTid와 커널 tid, 시각 및 command를
대조한다. 식별자를 통신 예약 필드에 넣거나 ABI를 변경하지 않았다.

`FilterSendMessage`는 HRESULT를 반환한다. DLL의 `GetLastError` 표기는 그 반환값을
변환한 최종 오류이고, `lastErrorSnapshot`은 API 직후의 스레드 마지막 오류 참고값일 뿐이다.
둘이 다르면 HRESULT와 최종 반환값을 우선한다.
[Microsoft FilterSendMessage 설명](https://learn.microsoft.com/en-us/windows/win32/api/fltuser/nf-fltuser-filtersendmessage)

## 4. 커널 출력은 선택적으로 추가 수집

커널 진단은 SYS에 포함되어 있으며 **UI 로그 파일에 자동 저장되지 않는다**.
최신 SYS를 실제로 로드한 시험 VM에서, 커널 출력 수집이 설정된 WinDbg 등으로
`[UF][control]` 메시지를 저장한다. 수집 환경이 없으면 우선 위 사용자 모드 로그 3개만 전달한다.
디버그 출력은 필터 마스크·수집 설정에 영향을 받으므로 출력이 없다고 커널 미진입을 단정하지 않는다.
레지스트리·부팅 디버그 설정을 프로그램이 자동으로 바꾸지는 않는다.
[Microsoft DbgPrintEx 설명](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-dbgprintex)

수신 `command=5/6`, SET 입력 24바이트, QUERY 입력 16/출력 40바이트, 프로토콜 2를
확인한다. `stage=command-unsupported`, `header-reject`, `boot-set-*-reject`,
`boot-query-*-reject`, `message-exception`, `message-exit`을 대조하면 거부 위치를 구분할 수 있다.

## 5. 파일 교체와 메모리 로드를 구분

- 현재 파일 드라이버 설치는 패키지 설치 후 `FilterLoad`를 요청하며, 이미 로드된 경우도
  성공으로 처리한다. 이번 로그 추가에서는 이 동작을 바꾸거나 자동 언로드하지 않았다.
- 실행 폴더 SYS, DriverStore/서비스 `ImagePath`의 SYS, 메모리에 로드된 SYS는 같은 버전이라고
  가정하지 않는다. 디스크 파일 해시가 같아도 메모리 이미지의 교체를 증명하지는 않는다.
- 배포 스냅숏은 연결 세대별 첫 보호 요청에서 읽기 전용으로 수집한다. 로컬 고정 드라이브의
  일반 파일만 대상으로 하며 경로·권한·크기 등의 이유로 조회를 생략해도 보호 명령은 계속한다.
- 커널 빌드 표식은 실제 실행된 진단 SYS의 식별 근거다. SYS를 교체·재로드하는 시험은
  검사점이 준비된 VM에서만 수행하고, 재부팅 필요 여부와 로드 결과를 별도로 기록한다.

현재 기능과 제한은 [1차 구현 문서](파일필터_부트보호_구현.md), 후속 구조 변경은
[2차 계획](부팅영역보호_2차계획.md)을 따른다.

## 6. 이번 진단본 검증 결과

- 전체 Debug x64 Rebuild: 성공, 경고 0·오류 0, 21.38초.
- 전체 Release x64 Rebuild: 성공, 경고 0·오류 0, 22.56초.
- 두 구성에서 파일 부트 순수 로직 44개, 실제 DLL 미연결/ABI 13개, UI 진단·표시 43개
  검사가 각각 통과했다. 기존 파일 자체 시험도 종료 코드 0이다.
- 실제 DLL 소스를 포함한 전송 모의 시험은 `/W4 /WX` 빌드와 41개 검사를 통과했다.
  `HRESULT=0x80070001`과 반환 오류 1의 보존, 실패 출력 초기화, 잘못된 응답과
  단계 로그를 확인했다. 통신을 모의 함수로 대체했으므로 실제 커널 검증은 아니다.
- 최종 Debug UI의 10개 합성 화면과 중복 요청·지연 취소·상태 표시 회귀 검사가 통과했다.
- Debug/Release 공용 bin의 SYS·DLL 해시가 각 빌드 원본과 일치했다.
- 최초 Release 빌드에서 커널 날짜 매크로 사용이 거부되어 명시적 진단 개정 표식으로
  수정한 뒤 두 구성 전체를 다시 빌드했다. 이전 실패 로그도 삭제하지 않았다.
- DLL 구성 표식은 CRT의 `_DEBUG` 여부를 추측하지 않고 프로젝트의 실제 Configuration으로
  기록한다. 최종 Debug/Release DLL의 로그에서 각각 올바른 구성명을 확인했다.

최종 빌드 로그는 `artifacts/file-boot-diagnostics-debug-verified.log`와
`artifacts/file-boot-diagnostics-release-verified.log`, 합성 UI 화면은
`artifacts/file-boot-diagnostics-ui-final`에 보관했다. VM 설치·재현 및 실제 커널 출력 수집은
수행하지 않았다. 사용자 VM에서 로그를 받은 뒤 오류 1의 원인을 확정해야 한다.
